Methodology

What makes the numbers credible

  • One scenario per architectural choice (01–08 in the sample harness)
  • Multiple runs per variant — full profile for production decisions
  • Build time, image size, startup to readiness endpoint
  • p95 startup and regression checks in CI
springdocker benchmark generate --project-root .
springdocker benchmark run --profile full --runner-arg=--skip-native
springdocker benchmark analyze benchmarks/03-custom-jre-jlink/results/raw.csv
Caveats

Threats to validity

Host variance

Absolute ms change across laptops and CI runners.

Workload shape

Web API vs batch vs CPU-heavy changes the winner.

Competing goals

Cold start, throughput, and image size rarely align.

Use findings as decision guidance for your service — not universal laws.

Decision 01

Adopt specialized stages as default

Simpler two-stage layout can win on startup alone — but pays heavily in build time and image size.

When to override

Scenario 02 · highest ROI

BuildKit cache mounts

3,410 msWithout cache
622 msWith cache

~5.5× faster rebuild after touching one Java file

RUN --mount=type=cache,target=/root/.m2 \
    ./mvnw package -DskipTests
Decision 02

BuildKit cache ON by default

  • Critical for ephemeral CI runners with no warm local .m2
  • Pair with layered JAR for registry-level cache hits too
  • Disable only when the platform cannot support deterministic cache behavior

Decision 03

Use jlink + jdeps with curated must-have modules

jlink --add-modules java.base,java.logging,… \
  --strip-debug --compress=2 --output /customjre
  • ~30% smaller image with similar startup in our sample
  • Merge must-have.txt modules jdeps misses (JNDI, logging, desktop APIs)
  • Skip only when compatibility or tooling blockers are proven on your app

Scenario 05

JVM container flags

Quick profile

One variant can look like a clear winner.

Full profile

Different host sensitivity — winner can flip.

-XX:+UseContainerSupport
-XX:MaxRAMPercentage=75
-XX:+ExitOnOutOfMemoryError
-Djava.io.tmpdir=/tmp
Decision 05

Ship safe baseline flags first

  • Container-aware memory policy + fail-fast on OOM
  • Aggressive GC tuning only after service-specific benchmarking
  • GC logging is non-negotiable when distroless removes shell debugging

Decision 07

Choose by workload shape — benchmark both paths

Native wins when

Cold start and footprint dominate (scale-to-zero, edge, burst traffic).

JVM wins when

Sustained throughput, fast iteration, and reflection-heavy stacks matter.

AppCDS class archive

# Train at build
java -XX:ArchiveClassesAtExit=app.jsa -jar app.jar
# Load at runtime

Decision 08

Enable AppCDS when using layered JAR builds

  • Train archive in build stage; ship .jsa with the image
  • Lower startup latency without native-image complexity
  • Compare against end-to-end readiness — not isolated micro-benchmarks alone

What to do next

  1. Enforce policy baseline — non-root, digests, SBOM, verify in CI
  2. Enable BuildKit cache on every Java Docker build
  3. Run one full-profile benchmark on a real service
  4. Adopt only changes with repeatable p95 or cost improvement
